# Realtime overload and deploy failure — 2026-10-04

The widget sent a read receipt after every Svelte update. Each receipt was persisted/published even if already applied, then echoed back into the widget's update cycle. The Node WebSocket gateway forwarded all events to Mautic without bounded concurrency. This feedback loop saturated the 20-worker PHP-FPM pool and Nginx's socket/file descriptor capacity.

Nginx recorded 77,469 failed ingest requests during the ten minutes before the reboot, with peak minutes exceeding 13,000 requests. System activity showed approximately 99.6% CPU busy across the four cores. Stopping the gateway ended the request storm and the load declined to around 0.2.

The frontend deploy failed separately during type checking with SIGKILL. The kernel confirmed an out-of-memory kill of Node at that same timestamp. The frontend build was configured for a 6 GiB Node heap on a 7.6 GiB server also running four Next processes, MySQL and Mautic. Local WebChat asset builds were used for this repair.

## Repair

- SSE broker in PHP CLI/Workerman, supervised by systemd with CPU/memory/buffer/connection bounds.
- Authenticated HTTP commands go directly to Mautic; the broker only distributes events and never calls FPM or the database.
- Client receipt high-water marks and monotonic server policy stop repeated reads and status regression.
- Typing events are throttled and indicators expire automatically.
- Human/visitor reads survive history reload, sending is acknowledged over HTTP, and SSE replay is bounded with durable history recovery.
- Inbox metadata/identity queries are batched, history is scalar, and receipt writes are constant-count transaction statements.
- Three targeted indexes were applied after a new verified full backup; EXPLAIN selected the list/latest-direction indexes.
- AI work runs outside HTTP/FPM through the supervised Inbox worker.

## Validation

DB-free tests exercise PHP broker authentication, room isolation, typing, receipt delivery, reconnect/replay and its memory bound. Client tests send 1,000 UI updates and assert exactly one receipt and one typing transition. The Inbox suite has 53 passing frontend checks.

Browser checks on an authorized validation conversation confirmed visitor-to-Inbox delivery, both typing indicators, Inbox-to-widget reply without reload, unread count while minimized, clearing unread on open, and history/read-state retention after reload. No destructive database tests, fixtures or schema reset were run on production.

The running broker used about 15 MiB and remained stable without restarts during verification. Deployment does not imply that the separate Next frontend build's memory budget has been changed.
